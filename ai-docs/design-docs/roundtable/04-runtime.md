# 运行模型

## 一场会的生命周期

```
load      读取 table.md 与 seats/*.md，校验，等调用方传入主题
  ↓
discuss   所有席位并发讨论，按等待规则推进，直到全员静默或时间到
  ↓
judge     程序裁决（投票 / 否决 / 阈值）
  ↓
loop      未通过时按 onVeto 与 maxAttempts 决定重来或收手
  ↓
finalize  写会议记录，返回结构化结果
```

## 发言池

一场会有一个**发言池**，所有席位说过的话都会实时追加进去。

```
发言池 = [
  { seat: "grom",   content: "这个方案我们店做不到" },
  { seat: "jaina",  content: "开头太平，读者会划走" },
  { seat: "grom",   content: "不过第三个动作可以试" },
  { seat: "medivh", content: "平均寿命 15 个月这句缺出处" }
]
```

**池是共享的、只追加的。** 所有席位看到同一份内容，**包括自己说过的话**。

## 席位工具

席位可以在 `seat.tools` 中声明允许使用的工具名称。调用方通过 `runRoundtable({ tools })` 提供对应的 schema 和 handler。

```ts
await runRoundtable({
  configDir,
  tools: {
    'topic-history.check': {
      name: 'topic-history.check',
      description: '检查历史主题是否重复',
      parameters: schema,
      execute: async (input, context) => lookupHistory(input, context)
    }
  }
})
```

一次席位调用可以经历多次模型请求和工具返回，直到模型给出最终发言。工具调用受 `seat.maxToolCalls` 限制，工具结果不单独进入发言池，调用记录挂在对应 statement 上。CLI 不能凭配置自行发现业务 handler，项目需要使用 API 注入工具或提供自己的宿主进程。

## 等待机制

这是圆桌最重要的机制，决定「讨论」是否成立。

### 规则

一个席位发言并入池后，**必须等到池里出现比「自己最新那句」更新的发言**，才能发起下一次请求。

```
A 说 → 池 [A]        A 等待
B 说 → 池 [A,B]      A 看到新增 → 可以再说
A 说 → 池 [A,B,A]    A 等待；B 看到新增 → 可以再说
```

### 为什么必须等待

不等的话，循环发完立刻再发，一个人会连续输出十几句，别人插不进来——那不是讨论，是各说各话。

实测（无等待机制，3 分钟）：

| 席位 | 发言条数 |
| --- | --- |
| 格罗姆 | 61 |
| 萨尔 | 55 |
| 乌瑟尔 | 54 |
| 麦迪文 | 33 |
| 吉安娜 | 1 |

一个人在 3 分钟里说了 61 句。

### 为什么等待够用

**自己说完后，池里最新一条就是自己的。** 因此自己绝对无法连说，必须等别人开口。

这同时解决了「是否需要发言次数上限」：等待本身就是天然限流，**不需要 `maxTurns` 之类的参数**。

### 节奏由讨论决定

别人说得快就接得快，对方沉默就安静等待。这正是真实对话的样子。

## 退出与唤醒

### 两个状态

| 状态 | 含义 |
| --- | --- |
| `active` | 参与讨论，按等待规则发言 |
| `quiet` | 自己负责的事已有结论，不再主动开口；被点名可回到 `active` |

### 退出：`done`

模型在返回里给出 `done`。**它不是结论本身，是「我这边说完了」的标记。**

判定标准由圆桌库**统一定义**，写进公共提示词，不由项目各写一遍——否则每个席位理解不同，机制会失效。

| 类型 | 例子 | `done` |
| --- | --- | --- |
| 确定结论 | 「合规上我没意见，全文没有触发退稿事项的内容」 | `true` |
| 确定结论 | 「这几处我都查过，站得住」 | `true` |
| 观点 | 「开头太平，读者会划走」 | `false` |
| 观点 | 「我们店做不到」 | `false` |
| 附和 | 「同意吉安娜」 | `false` |
| 提问 | 「麦迪文，事实这块你看呢」 | `false` |

**区分标准是「是否还能被继续讨论」**：

- 「合规上我没意见」是终局，除非有人提出新的合规问题，否则没得聊
- 「开头太平」是观点，别人可以说「我觉得挺好」，还能继续

`done: true` 的席位转入 `quiet`，**不退出会议**，只是不再主动开口。

### 唤醒

其他席位的发言中如果出现某个 `quiet` 席位的 `name` 或 `id`，该席位回到 `active`。

用文本匹配实现。实测中萨尔确实说过「麦迪文，事实这块你看呢」，模型会主动点名。

**这是本机制的已知弱点**：如果模型不写名字，静默的席位就不会被唤醒。缓解方式是席位提示词里鼓励点名，但不保证。

### 全员静默即结束

所有席位都是 `quiet`，池子不再增长，讨论自然结束——**不必等满 `durationMs`**。

讨论该结束时提前结束，这是收益不是缺陷。

## 可见性

**没有 `sees` 参数。** 所有席位共享同一份上下文：

- 议题 `topic`
- 背景 `brief`
- 材料 `context`
- 全部发言（含自己的）

「独立判断」在真实圆桌里指的是「不附和别人」，应该靠席位提示词约束，不是靠技术隔离。切断可见性会让席位拿不到互相接话所需的上下文。

实测证据：旧版 `sees: none` 的席位在 3 分钟里说了 54 条几乎逐字相同的发言——因为它每次拿到的输入完全相同，没有新信息可反应。

## 返回结构

```json
{
  "reason": "合规上我没意见，全文没有触发退稿事项的内容。",
  "done": true,
  "verdict": "pass",
  "score": 20
}
```

| 字段 | 用途 |
| --- | --- |
| `reason` | **发言内容**。入池、展示、记录都用它 |
| `done` | 我负责的事有结论了，转 `quiet` |
| `verdict` | 供程序裁决，`pass` / `reject` |
| `score` | 可选，模型给的评分 |

`reason` 是自然语言的一句话。**席位不在发言里宣布「能发/不能发」**，裁决由程序完成。

## 提示词的内容

每次调用带四块内容，分区标注：

| 区块 | 内容 | 来源 |
| --- | --- | --- |
| 议题 | 这场讨论要回答什么 | `topic`（必填） |
| 背景 | 为什么开这场会 | `brief`（可选） |
| 材料 | 桌上摆的东西，逐条编号 | `context`（可选） |
| 前序发言 | 池里已有的全部发言 | 圆桌维护 |

前三块是外部输入，第四块是讨论过程。

## 裁决由程序做

**模型永远不返回最终通过与否。**

| 谁 | 产出 | 不产出 |
| --- | --- | --- |
| 席位 | `verdict`（`pass` / `reject`）、`score` | 最终结论 |
| 圆桌程序 | 依据 `canVeto`、`weight`、阈值算出通过与否 | — |

```
本场结论 =
  若任一 canVeto 席位给出 veto              → 否决
  否则若 加权通过票 / 加权总票 ≥ threshold  → 通过
  否则                                     → 否决
```

席位在讨论中可以多次发言，但**投票只取它投出的判断**。同一席位多次 `verdict` 时，以最后一次为准。

## 一票否决

`canVeto: true` 是强权力，**任一否决即否决**。多人表决用 `weight` 表达，两者不混用：

| 需求 | 用哪个 |
| --- | --- |
| 某席位说了不就不能过 | `canVeto` |
| 多人同意就能过 | `weight` + `threshold` |
| 少数人反对要压过多数 | 改用 `canVeto` |

## 成本控制

| 控制项 | 管什么 | 触顶行为 |
| --- | --- | --- |
| `durationMs` | 整场时长 | 不再发起新请求 |
| `maxPoolTokens` | 每次请求的输入长度 | 丢弃池内最早发言 |
| `seat.maxTokens` | 单次调用的输出上限 | 模型输出被截断 |

**不设调用次数预算。**

### 思考型模型

思考型模型（如 GLM-5.3-Flash）先产出内部推理，再产出正文，**两者共用 `max_tokens`**。80 token 时推理把额度吃光，正文返回空串。

且推理长度随发言池增长，`maxTokens` 追不上。

解法是 `table.md` 的 `reasoningEffort`，项目按需声明。圆桌**不提供默认值**，由厂商默认决定；项目可以选择 `low` 让推理归零，速度提升近 9 倍。

## 失败与退路

| `fallback` | 行为 |
| --- | --- |
| `skip`（默认） | 该席位停止发言并转 `quiet`，记 `skipped` |
| `retry` | 按 `@ci-kit/ai` 的 `retries` 重试；仍失败则按 `skip` |
| `abort` | 立即终止整场会，状态 `aborted` |

**默认 `skip`** 的理由：讨论中一个人掉线不该散会，但它的缺席必须被记录，不能被当成同意。

失败分类沿用 `@ci-kit/ai` 的 `AiError.kind`：

| kind | 是否重试 |
| --- | --- |
| `quota` / `server` / `network` | `retry` 下重试 |
| `auth` / `config` / `request` | 不重试 |
| `output` | 不重试（付费调用可能已成功） |

### 只剩一个存活席位

它等不到更新，会一直等到 `durationMs`。这是可接受的：真实会议里只剩一个人，他也不会自言自语。不做特殊处理，避免引入共享存活状态。

## 幂等与续跑

| 场景 | 行为 |
| --- | --- |
| 同一次会重复执行 | 已通过则直接返回结果，不再调用模型 |
| 中途中断 | `--resume <run-dir>` 从 `state.json` 记录的进度继续 |
| 已完成而重跑 | 复造记录，不重新调用 |
| 修改席位或 table | 视为**新的一场会**，不续跑 |

### 续跑怎么做

- 已产生的发言保留在池里，作为前序发言
- 剩余时间 = `durationMs - (now - startedAt)`
- 剩余时间不足则直接进入裁决

### 状态机

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `running` | 正在讨论 | 否 |
| `passed` | 裁决通过 | 是 |
| `rejected` | 轮次用尽仍未通过 | 是 |
| `aborted` | 触发 `abort` | 是 |
| `failed` | 配置或环境错误 | 是 |

`finishedAt` 只有终态才写。

## 上下文（context）

圆桌不采集，`context` 由调用方传入，原样分发给所有席位。

| 形态 | 说明 |
| --- | --- |
| 字符串 | 直接作为文本上下文 |
| 数组 | 逐条编号后分发 |

`context` 与发言池是两回事：前者是外部材料，后者是讨论过程。

## CLI 形态

```bash
ci-kit-roundtable run --config .ci-kit/roundtable --topic "这篇能不能发" --out roundtable-out
ci-kit-roundtable run --config .ci-kit/roundtable --topic "…" --context-file article.md
ci-kit-roundtable init  .ci-kit/roundtable
ci-kit-roundtable check --config .ci-kit/roundtable
```

`--topic` 必填。`--context` 接收文本本身，`--context-file` 从文件读，两者可重复。

**传长文本时用 `--context-file`**：实测在 PowerShell 里传多行内联字符串会因为引号和换行处理而丢失内容。

`check` 不产生任何付费调用，适合放进 CI 前置检查。
