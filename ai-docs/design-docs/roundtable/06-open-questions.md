## 需要观察后决定

| 事项 | 观察什么 | 当前取向 |
| --- | --- | --- |
| `durationMs` 默认 3 分钟是否合适 | 实际能聊出几轮 | 3 分钟；项目可覆盖 |
| `maxPoolTokens` 默认 3000 是否合适 | 3 分钟讨论是否经常触顶 | 3000；只有模型极快时才触发 |
| `seat.maxTokens` 默认 600 是否合适 | 思考型模型的推理长度会波动，600 是否总有正文余量 | 600，实测正文稳定在 20 余字 |
| 同一席位多次 `verdict` 的取舍 | 「以最后一次为准」是否符合直觉 | 以最后一次为准 |
| `threshold` 默认 0.5 是否合适 | 是否频繁需要调高或调低 | 0.5 |
| `weight` 的实际使用频率 | 若几乎无人使用，考虑简化为一票一权 | 保留 |
| `invalid-veto`（空理由否决）是否要更严格 | 若出现「否决但不给理由」的滥用 | 记 `invalid-veto`，不计入 |

## 明确不做（不属于本包）

| 事项 | 理由 |
| --- | --- |
| 内置角色库 | 违反「Prompts are business assets」；用 `init` 生成示例替代 |
| 内置阶段语义（提案 / 审核 / 收口） | 圆桌不认识角色；这些是项目的表达 |
| 串行 / 并行模式开关 | 讨论天然并发，没有第二种形态 |
| 采集器（RSS / 网页 / 数据库） | 圆桌只接收 `context`，采集由调用方负责 |
| 模型供应商适配 | 统一走 `@ci-kit/ai` |
| 定时调度 | 由 CI 负责 |
| 席位 `extends` 继承 | 等真的出现重复写再抽 |
| 流式输出 | CLI / CI 场景下对日志和管道无价值 |
| Web / 可视化界面 | 先跑通 CLI 与 Markdown |
| 独立发版 | 跟随 monorepo 统一版本 |

## 与上一版设计的差异

上一版有「阶段 × 执行模式」：每个阶段可以 `serial` 或 `parallel`，席位被强制分配到阶段，`propose` / `converge` 带特殊语义，`sees` 支持 `lead-only` 和席位列表。

现在全部去掉。**圆桌只有一场讨论**：所有人同时在场，由时间划定长度，发言实时共享。流程仍是「讨论 → 结论」，但讨论内部没有任何机械切分。
