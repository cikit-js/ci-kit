# 定位与边界

## 它是什么

`@ci-kit/roundtable` 是**编排引擎**：按人写好的席位与议事规则，调度多个 AI 依次发言，产出可裁决、可追溯、可续跑的会议记录。

它不认识「选题」「文章」「审稿人」这些业务词，只认识四种抽象：

| 抽象 | 含义 | 现实对应 |
| --- | --- | --- |
| **席位** | 谁坐在桌边、什么身份、怎么说话 | 人写 `.md` 定义 |
| **议事规则** | 怎么发言、谁能看见谁、谁说了算 | `table.md` |
| **桌面** | 桌上摆什么、产生了什么 | 外部传入的上下文 + 会议记录 |
| **产物** | 这一场会做成了什么 | 会议记录 + artifacts |

把某个具体业务（例如内容生产流水线）搬上圆桌，是使用者用这些抽象去**表达**的过程，不是圆桌内置的能力。

## 它不是什么

| 不是 | 理由 |
| --- | --- |
| 不是角色库 | 预设角色违反 README 的「Prompts are business assets: they live in each project」；开箱可用性用 `--init` 生成示例解决，不把示例当运行时依赖 |
| 不是模型适配层 | 文本调用统一走 `@ci-kit/ai` 的 `text()`，供应商由 `AI_TEXT_PROVIDER` 决定 |
| 不是采集器 | 素材由使用者传入，圆桌不抓 RSS、不读网页、不扫数据库 |
| 不是决策器 | 裁决由程序按规则判定，模型只提供判断材料 |
| 不是流式大会 | CLI/CI 场景下流式对日志和管道无价值，一次性输出 |

## 为什么单独成包

现有 README 的设计规则是：

> - Modules do not depend on each other except through `@imba97/ci-kit-http`.
> - Prompts are business assets: they live in each project, not in this package.

放进 `@ci-kit/ai` 会让它从「一次调用」膨胀成「一个框架」，且改议事制度会逼所有用 `text` 的人跟着升版本。

新包的依赖方向：

```
roundtable ──> ai（调用 text()）
           └─> http（不直接用，保持设计规则一致）
```

## 议题不是参数

这是本设计的核心判断，也是它区别于普通批处理的关键：

> **圆桌开一场会，不需要人给方向。**

```
空桌 → 有 canPropose 的席位提议题
     → 其他席位附议 / 反驳 / 补充
     → 达成共识后进入下一阶段
     → 有人产出，有人审核，有人收口
```

「议题」是**一种发言产出**，是 `propose` 阶段的第一条记录，与其他记录地位相同。

这一条让圆桌彻底通用：内容号用它选选题，研发用它挑技术债，客服用它找客诉共性问题，动作都是「席位先提议题」。

人工指定议题是**可选覆盖**（对应 `--topic`），用于人工校准或复盘，不是常态输入。无人值守的定时任务不应依赖它。

## 能力边界验证

`wukong-content`（悟空搭档公众号流水线）只作为**能力验证样例**：如果圆桌的表达能覆盖它的能力，说明抽象够用；覆盖不了，说明缺了一层。它不是实现目标，也不要求圆桌能「复刻」它。

| wukong-content 现状 | 圆桌中的表达 |
| --- | --- |
| `select.md` 选题 | 席位 `editor`，`canPropose: true`，阶段 `propose` |
| `write.md` 写作 | 席位 `writer`，阶段 `produce` |
| `review.md` 审稿 | 席位 `guard`，`sees: none`，`canVeto: true` |
| 最多 3 稿 | `table.md` 的 `maxAttempts: 3` |
| 12 次文本调用预算 | `budget: { total: 12 }` |
| 换角度重写 | `onVeto: re-propose` |
