# 席位（seat）

一个 AI 一个 Markdown 文件，放在 `.ci-kit/roundtable/seats/` 下。

- **frontmatter** = 元数据，分组书写；
- **正文** = 这个席位的职责说明，作为系统提示词的主体。

## 目录

```
.ci-kit/roundtable/seats/
├── editor.md
├── writer.md
├── guard.md
└── host.md
```

文件名不参与语义，`id` 才是锚点。文件名可以带排序前缀（`01-editor.md`），但那只为方便人翻目录，不影响运行。

## frontmatter 分组

三个**不分组**的顶层字段，加三个**分组**。

| 位置 | 字段 | 必填 | 含义 |
| --- | --- | --- | --- |
| 顶层 | `id` | 是 | 席位唯一标识，程序锚点 |
| 顶层 | `role` | 是 | 职能，用于展示与日志 |
| 顶层 | `enabled` | 否 | `false` 表示本次不参会，默认 `true` |

| 分组 | 装什么 | 为什么单独成组 |
| --- | --- | --- |
| `identity` | 名字、头像、头衔、背景 | 都是「这个人是谁」 |
| `persona` | 立场、性格、风格、说话方式、价值观、口头禅、禁区 | 都是「这个人怎么想、怎么说」 |
| `seat` | 工具权限、否决、权重、预算、退路 | 都是「这个人在桌上有多少权力」 |

分组的实际收益：讨论跑偏先查 `persona`，流程乱序先查 `seat`；将来若支持 `extends`，可以只覆盖 `persona` 而保留 `seat`；同一角色换场合只改 `persona`。

### identity

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `name` | string | 回落到 `role` | 席位名字，可拟人，如 `周慎` |
| `avatar` | string | — | emoji 或图片名，用于记录中区分席位 |
| `title` | string | — | 一句话人设，如 `跑了六年餐饮一线的老编辑` |
| `background` | string | — | 背景设定，供模型建立判断依据 |

名字的作用不只是好看：记录里 `周慎：……` 比 `guard：……` 易读，交叉引用时「回应老周的质疑」也比「回应 guard 的质疑」自然。

### persona

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `stance` | string | — | **决策倾向**，如 `宁可错杀，不可放过` |
| `personality` | string[] | — | 性格特质，如 `[较真, 不留情面]` |
| `style` | string | — | 表达风格，如 `冷静、逐条、不绕弯` |
| `speech` | string | — | 说话习惯，如 `爱用反问；不说「总体而言」` |
| `values` | string | — | 价值观或原则 |
| `quirks` | string | — | 小习惯或口头禅 |
| `avoid` | string | — | 禁区，如 `不评价营销策略；不提具体金额` |

#### 性格参数要写「可被检测的行为」

模型对 `style: 直接` 几乎无感；但 `speech: 爱用反问；不说「总体而言」` 能被遵从，因为它**可观测**。

因此写参数时优先写行为约束，不堆形容词：

| 差 | 好 |
| --- | --- |
| `style: 犀利` | `speech: 先给结论再给理由，一次只问一个问题` |
| `personality: [专业]` | `personality: [对数字敏感，看到百分比必追问口径]` |

#### 表达性格与决策倾向必须分开

| 用途 | 影响什么 | 参数 |
| --- | --- | --- |
| 表达性格 | 语气、措辞、举例 | `personality` / `style` / `speech` / `quirks` / `avoid` |
| 决策倾向 | 判断方向：保守、激进、先验证 | `stance`（显式声明） |

如果性格既影响表达又隐式影响判断，讨论结果会**无法复现**：同一份记录，换个人读出不同结论。所以：性格只决定**怎么说**，`stance` 显式声明**怎么判**。

### seat

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `canVeto` | boolean | `false` | 一票否决权 |
| `weight` | number | `1` | 表决权重 |
| `maxTokens` | number | `600` | 单次调用的正文预算；思考内容不计入这个字段的语义 |
| `tools` | string[] | `[]` | 允许调用的工具名称。handler 由调用方注册，库不实现业务工具 |
| `maxToolCalls` | number | `4` | 一次席位发言最多调用多少次工具 |
| `fallback` | `skip` \| `retry` \| `abort` | `skip` | 调用失败时的策略 |
| `output` | `text` \| `json` | `text` | 产出类型；`json` 才能投出结构化判断 |

席位**不声明自己参加哪场讨论**。谁在场由 `table.md` 之外决定：所有 `enabled: true` 的席位同时参加那一场讨论。

#### 三个最关键的字段

1. **`maxTokens`** — 单次调用的输出上限。思考型模型的推理与正文共用这个额度，需要配合 `table.md` 的 `reasoningEffort` 使用。发言的长短靠席位提示词里的「只说一句话」控制，这个字段只防跑飞。
2. **`maxTokens` + `fallback`** — 发言长度由 `maxTokens` 封顶，避免变成长篇大论；`fallback` 防止单个席位拖死整场会。

#### maxTokens 是「正文预算」，不是「席位能说几个字」

思考型模型（如 GLM-5.3-Flash）先产出内部推理，再产出正文，两者**共用同一个 `max_tokens` 上限**。按「一句话 20 字 ≈ 60 token」来定这个值，推理就会把额度吃光，正文返回空串，席位整场失声。

实测 GLM-5.3-Flash 在圆桌提示词下：80 token 正文为空（`finish_reason: length`）；600 token 能输出 20 余字正文，但会一次收口五个字段的席位仍然截断。

**因此默认 1000**，且这个字段的语义是「留够推理之后再给正文留余量」，不是字数换算。真实编前会实测：普通发言不超过 102 token，收口那一条要 248 token；1000 让两类发言都留出三倍以上余量，模型写完 JSON 自然停止，不会因为上限高就写成长篇。

圆桌不提供独立的思考预算配置。控制发言长短靠席位提示词里的「只说一句话」，`maxTokens` 只负责防止跑飞。
3. **`canVeto`** — 让圆桌能表达「有的事必须一票否决」。任一可否决席位否决即为否决，多人表决用 `weight` 表达，两者不混用。

## 完整示例

```markdown
---
id: guard
role: 事实审核

identity:
  name: 周慎
  avatar: 🛡️
  title: 做了十年事实核查的老审核
  background: 做过十年媒体事实核查，见过太多「有出处但没出处对」的引用

persona:
  stance: 宁可错杀，不可放过
  personality: [较真, 不留情面, 对引用敏感]
  style: 冷静、逐条、不绕弯
  speech: 说话像写核查单，每条只问一句话
  values: 一条没有原文支撑的观点，等于没有观点
  quirks: 看到数字就要追问口径和日期
  avoid: 不做风格评价，只管事实

seat:
  canVeto: true
  weight: 2
  maxTokens: 1000
  tools: [topic-history.check]
  maxToolCalls: 2
  fallback: skip
  output: json
---

你负责核对每个观点是否有依据。

## 职责
- 逐条核对发言中的事实、数字、引用
- 无法核实的，明确标出「缺证」，并给出最小核查动作
- 不评价文风、结构、营销价值

## 输出
每条只写三样：哪句话、缺什么、怎么补。
```

## 工具权限

`tools` 只声明席位允许请求哪些名称。工具的参数 schema 和执行 handler 由调用方通过 `runRoundtable({ tools })` 注册，圆桌库不认识 RSS、网页、数据库或业务规则。

工具调用发生在一席位的一次发言内部。模型请求工具后，库校验名称和参数，执行 handler，把结果放回模型上下文，直到模型返回最终 speech 或结构化回复。工具调用不会单独进入共享发言池，但会随该条 statement 记录。

工具应保持只读、可重复和有界。调用方负责限制网络、耗时、返回长度和敏感信息。工具结果按外部资料处理，不能改变会议规则。

## 解析规则

| 规则 | 行为 |
| --- | --- |
| 未知分组报错 | 写错成 `personna` 必须报错，不得静默忽略 |
| 分组内未知字段报错 | `persona: { temper: xxx }` 报错，防止「写了但不生效」 |
| 必填缺失报错 | 缺 `id` 或 `role` 直接失败，不猜默认值 |
| `id` 重复报错 | 两个席位同一 `id` 报错，不取其一 |
| 扁平写法兼容一层 | 允许 `name:` 直接写在顶层，解析时归入 `identity`；同一字段两处都写则报错 |
| 类型错误报错 | `weight: "two"` 报错，不做隐式转换 |

扁平兼容是给既有项目留的余地：现在 `prompts/*.md` 都是扁平字段，将来若想把现有提示词迁成席位，不需要一次性重写。

## 渲染

圆桌不把参数原样塞给模型，而是拼成一段**席位人设**放在系统提示词前部。人只写参数，不手写模板。

```
你是周慎，一名做了十年事实核查的老审核。

## 背景
做过十年媒体事实核查，见过太多「有出处但没出处对」的引用

## 你的性格
较真、不留情面、对引用敏感

## 你的立场
宁可错杀，不可放过

## 你的说话方式
- 说话像写核查单，每条只问一句话
- 看到数字就要追问口径和日期

## 你的原则
一条没有原文支撑的观点，等于没有观点

## 你的边界
不做风格评价，只管事实

<!-- 以下为席位 md 正文，原样拼接 -->
你负责核对每个观点是否有依据。
...
```

拼接顺序固定：身份 → 性格 → 立场 → 说话方式 → 原则 → 边界 → 正文。空字段整段省略，不留空标题。
